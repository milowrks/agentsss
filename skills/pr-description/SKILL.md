# PR Description

```
PLAIN LANGUAGE, GROUNDED IN THE ACTUAL DIFF, IN THE FIXED TEMPLATE
```

Write (or rewrite) a PR description that matches the actual change and follows the template below. Keep it brief.

## Ground it in the diff first

Before writing, read what actually changed — don't infer from the task or memory:

- `git diff <base>...HEAD --stat` and `git log --oneline <base>..HEAD` for the file set and commits.
- Skim the substantive diffs so every claim is true of the code as it stands now (not an earlier plan).

Show the user the full description and get an explicit go-ahead before `gh pr edit` or `gh pr create`. Only open a PR when asked, always as `--draft`, and never with `--reviewer`.

Update an existing PR with `gh pr edit <n> --body-file <file>`, writing the file in the scratchpad.

## Template

Use these exact headings, in this order, with the emoji **after** the heading text. Add no other emoji. **Summary, Changes, and Verification are always included. Caveats is optional** — include it only when there is a real gotcha, trade-off, or non-obvious decision to flag, and drop the heading entirely otherwise.

```md
## Summary 🧑🏻‍💻

One or two sentences: what the PR does and its effect, in plain terms.

## Changes 🪵

- Bulleted list of what changed, grouped logically. Plain language; each bullet is a thing a reviewer can picture.

## Caveats ⚠️  (optional — omit the whole section when there's nothing)

The key thing a reviewer must know — a gotcha, trade-off, or non-obvious decision (link the relevant ADR/RFC/issue).

## Verification 🧪

- How it was checked (tests, build, manual). One bullet each.

Note: call out any limits on the checks (e.g. partial coverage) in a trailing plain-text note.
```

When the assistant drafted the description, attribute it the way the user's `~/.claude/CLAUDE.md` says for PR descriptions (currently a visible `🤖 Generated by Claude Code` first line, above `## Summary`).

## Voice

- **Plain language by default.** Reach for a technical term only when it is needed to describe a complex domain concept accurately — when the plain-English alternative would be vague, ambiguous, or wrong. Keep load-bearing terms (a specific API, mechanism, standard); cut decorative ones.
- **Brief.** Favour a short bullet over a paragraph. No filler, no restating the obvious.
- **No `## Test plan` section** — verification goes under Verification 🧪.
